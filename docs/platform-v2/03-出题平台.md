# 03 出题平台

> 目标：把今天**三套割裂的题目栈**收敛为一个「统一题目视图 + 统一可见性模型 + 完整单题出题流程」，并补齐文档/图片解析、翻译与终检。

## 1. 现状：三套题，三种规矩

| | 编程题 | 客观题 | 主观题 |
| --- | --- | --- | --- |
| 归属 | Java `problem-service` | Autolab | Autolab |
| 表 | `oj_problem` + `oj_problem_description` + `oj_problem_checkpoint_rel` | `problem_objective` | `problem_subjective` |
| 主键 | `problemId` / `problemCode`(`SDUOJ-<id>`) | `pid` | `pid` |
| 能否独立于题组存在 | **能** | **不能**（仅经 `problem_group` 绑定） | **不能**（同左） |
| 绑定方式 | 比赛/题单直接引 `problemCode` | `problem_group.problemInfo[].pid`，且 `problem_group.type=0` | 同左，`type=1` |
| 可见性 | `oj_problem.is_public` + `managerGroups` + 创建者 | **无** | **无** |
| 编辑权限 | 管理组 / 超管 | 题组的 `manageGroupId` / 超管 | 同左 |

**关键约束**：`problem_group.type` 是**组级**枚举（`0=选择 1=主观 2=编程`），即**一个题组只能装一种题型**。这是「三题型统一在题目页面」的最大结构性障碍。

## 2. 编程题的可见性：其实已经对了

这是需要澄清的一点。`ProblemService.queryProblemByPage()` 已实现：

```java
if (Role.SUPERADMIN.notIn(userSessionDTO)) {
    if (userSessionDTO != null) {
        query.and(o1 -> {
            o1.eq(ProblemDO::getIsPublic, 1)                                  // ① 公开
              .or(o2 -> o2.eq(ProblemDO::getIsPublic, 0)
                          .eq(ProblemDO::getUserId, userSessionDTO.getUserId())); // ② 私有：仅本人
            List<Long> problemIdList = getProblemIdListInManagerGroups(userSessionDTO);
            if (CollectionUtils.isNotEmpty(problemIdList)) {
                o1.or(o3 -> o3.in(ProblemDO::getProblemId, problemIdList));       // ③ 管理组
            }
        });
    } else {
        query.eq(ProblemDO::getIsPublic, 1);                                      // 未登录：仅公开
    }
}
```

`queryByCode()` 同样在单题维度做了校验（非公开题只有出题者、管理组和超管可读 —— 注意源码注释写的是「只有出题者和超管」，**注释已过时，实际包含管理组**）。

**所以用户要求的「私有 / 公开 / 管理组 / 超管」在编程题上已经成立**，缺的是：

1. **列表入口**：`/manage/problem/list` 只服务管理端；客户端没有「公开题库」与「组内题目」两个入口。
2. **客观题/主观题没有这套模型**——它们没有 `is_public`，也没有 `managerGroups`。
3. **「不再提供统一列表」**：需要把「全部题目」拆成 `公开` / `我的组` / `我的` 三个来源。
4. **前端没有过滤器**：管理库与客户端题库都只有一个 `searchKey`，没有按可见性/标签/难度筛选。

### 2.1 必须先修的越权（P0）

```python
# sduoj-autolab/server/objective.py:30
@router.post("/info")
async def info(data: dict = Depends(ser_objective_info)):
    db = objectiveModel()
    return makeResponse(db.get_info_by_id(data["pid"]))   # 只按 pid 查，无任何归属校验
```

`model/objective.py:9` 同样只按 `pid` 过滤。后果：**任何登录用户只要知道或猜到 `pid`，就能读到客观题的题干与正确答案 `answer`**；主观题 `server/subjective.py` 同构。

这是本方案里**唯一一个已确认的可直接利用的信息泄露**，必须在「统一可见性」落地**之前**修复。

同理，`ProblemGroup.problemInfo` 允许**任何 admin 把别人的私有题塞进自己的题组**（题组侧不校验 `isPublic`）。

## 2.2 必须先统一的 ID 语义（P0）

`(psid, gid, pid)` 三元组存在**双语义**：

| 场景 | 语义 |
| --- | --- |
| 管理侧（`problem_group.gid`、`problemInfo[].pid`） | **主键** |
| 学生/提交侧（`answer_sheet.ps_get_proInfo_cache(psid, gi, pi)`） | **题单内下标** |

```python
# sduoj-autolab/model/answer_sheet.py:529
async def ps_get_proInfo_cache(self, psid, gi, pi):
    gid, pid = await self.get_gid_pid_by_psid_gi_pi_cache(psid, gi, pi)
```

即同一路径里的 `pid`，在管理接口是主键、在作答接口是下标。**统一题目视图必须显式区分 `native_id`（主键）与 `position`（下标）**，否则会写出「以为在改 A 题、实际改了 B 题」的错误。这是 03 的硬前置。

另注：`problem_objective.pid` 与 `problem_subjective.pid` 各自自增，**会撞号**。统一 uid 必须带类型前缀（`obj:45` / `subj:45`），不能只用裸 `pid`。

## 3. 目标模型：统一题目视图

### 3.1 不合并存储，合并视图

三套存储各有成熟实现（判题、作答、统计都绑定在原表上）。**不做物理合并**，改为：

```sql
-- 统一题目索引（物化视图表，由事件/定时任务维护）
CREATE TABLE oj_unified_problem (
  uid           VARCHAR(63) PRIMARY KEY,      -- 'prog:123' | 'obj:45' | 'subj:46'
  kind          TINYINT NOT NULL,             -- 0=编程 1=客观 2=主观
  ref_id        BIGINT NOT NULL,              -- problemId / pid
  title         VARCHAR(255) NOT NULL,
  owner_id      BIGINT NULL,                  -- 编程题的 userId / 客观主观题的 username 映射
  visibility    TINYINT NOT NULL,             -- 0=私有 1=公开 2=组内
  manage_group_id BIGINT NULL,
  tags          VARCHAR(255) NULL,
  difficulty    TINYINT NULL,                 -- 新增，三题型通用
  created_at    DATETIME(6) NOT NULL,
  updated_at    DATETIME(6) NOT NULL,
  UNIQUE KEY uq_unified (kind, ref_id),
  INDEX ix_vis (visibility, manage_group_id),
  INDEX ix_owner (owner_id)
);
```

这样既保留既有实现，又能统一检索与统一权限判定。

### 3.2 可见性语义（三题型统一）

| 可见性 | 谁能查看 | 谁能编辑 | 谁能引用到题单/比赛 |
| --- | --- | --- | --- |
| **公开** `1` | 所有人（含未登录） | 仅属主 + 超管 | 任何人（**只引用，不可编辑**） |
| **组内** `2` | 该管理组全体成员 | 管理组全体成员 | 管理组成员 |
| **私有** `0` | 仅属主 + 超管 | 仅属主 + 超管 | 仅属主 + 超管 |
| 超管 | 全部 | 全部 | 全部 |

**注意**：公开题目「引用了但不能编辑」——编辑权仍属原出题者。这正是用户的原话。

### 3.3 客观题/主观题补齐可见性

```sql
ALTER TABLE problem_objective
  ADD COLUMN visibility TINYINT NOT NULL DEFAULT 0,
  ADD COLUMN manage_group_id BIGINT NULL,
  ADD COLUMN difficulty TINYINT NULL,
  ADD COLUMN title VARCHAR(255) NULL;

ALTER TABLE problem_subjective
  ADD COLUMN visibility TINYINT NOT NULL DEFAULT 0,
  ADD COLUMN manage_group_id BIGINT NULL,
  ADD COLUMN difficulty TINYINT NULL,
  ADD COLUMN title VARCHAR(255) NULL;
```

**迁移默认值**：历史数据全部为 `visibility=0`（私有）+ `manage_group_id = 所属题组的 manageGroupId`。这样行为**不劣化**——原本只有管理组能看到，迁移后仍是组内可见。

### 3.4 题组类型：从「组级」放宽到「题项级」

用户要求「三种题型统一在题目页面呈现」。现状 `problem_group.type` 是组级。方案：

**保留 `problem_group.type` 作为「主类型」以兼容旧代码，新增题项级 `kind`**：

```sql
-- problem_group.problemInfo 现在每项为 {pid, score, submitLimit, antiCheatingRate}
-- 新增 kind 字段：
-- {pid: 12, kind: 0|1|2, score: 100, ...}
```

- 旧数据无 `kind` → 回退到 `problem_group.type`（行为不变）。
- 新数据可混合三题型于同一题组。
- 前端题目列表按 `kind` 渲染不同卡片。

**风险**：`problem_set.groupInfo` 与前端大量逻辑依赖 `group.type`。因此**分两步**：先允许混合（写入 `kind`），读路径先支持再逐步放开写路径。

## 4. 单题出题全流程

一条题目从「想法」到「可上线」，共 9 个阶段。每阶段有**产物**与**准入条件**，对应一个 `AiResource(kind='problem_authoring')`。

```
① 思路描述 → ② 题意确定 → ③ 题面编写 → ④ 元数据配置
   → ⑤ 生成器/校验器/标程/SPJ → ⑥ 数据生成 → ⑦ 七项终检
   → ⑧ 人工实测 → ⑨ 发布上线
```

### 4.1 阶段与产物

| 阶段 | 产物 | 谁做 | 准入条件 |
| --- | --- | --- | --- |
| ① 思路 | `idea.md`：考察点、难度目标、来源 | 人（可 AI 辅助扩充） | — |
| ② 题意 | `spec.json`：输入/输出格式、数据范围、边界约定、时间/空间限制 | 人 + AI 起草 | 思路已确定 |
| ③ 题面 | `statement.md`：题面正文 + 样例 + 提示 | AI 起草 + 人定稿 | 题意已冻结 |
| ④ 元数据 | 标签、难度、来源、题面语言、限制、评测模板 | 人 | 题面已定稿 |
| ⑤ 程序 | `gen.cpp`（生成器）、`validator.cpp`（输入校验器）、`std.<lang>` ×3（标程）、`checker.cpp`（SPJ，可选） | AI 生成 + 人审 | 题意冻结 |
| ⑥ 数据 | `data/01.in ... 40.in` + `.out`、`data_manifest.json`（含每点 SHA-256） | 服务端作业 | ⑤ 全部通过编译 |
| ⑦ 终检 | 七项检查报告（见 §5） | 服务端作业 | ⑥ 完成 |
| ⑧ 人工实测 | 专用题链、用时、得分、代码、意见 | 真人 | ⑦ 全绿 |
| ⑨ 发布 | 写入 `oj_problem`（或客观/主观表）+ 题组绑定 | 人确认 | ⑧ 通过 |

### 4.2 数据模型

```sql
CREATE TABLE oj_authoring_package (
  id            VARCHAR(63) PRIMARY KEY,
  unified_uid   VARCHAR(63) NULL,            -- 发布后回填
  owner_id      BIGINT NOT NULL,
  stage         VARCHAR(24) NOT NULL,        -- idea|spec|statement|metadata|programs|data|audit|human|published
  title         VARCHAR(255) NOT NULL,
  spec          LONGTEXT NULL,               -- spec.json
  statement     LONGTEXT NULL,               -- statement.md
  assets        LONGTEXT NULL,               -- 文件清单 [{name, sha256, kind}]
  checks        LONGTEXT NULL,               -- 七项终检结果
  human_trial   LONGTEXT NULL,               -- 实测记录
  version       INTEGER NOT NULL DEFAULT 1,

);

CREATE TABLE oj_authoring_human_trial (
  id             VARCHAR(63) PRIMARY KEY,
  package_id     VARCHAR(63) NOT NULL,
  trial_token    VARCHAR(64) NOT NULL UNIQUE,   -- 专用链接令牌
  solver_name    VARCHAR(64) NOT NULL,          -- 校验人姓名
  started_at     DATETIME(6) NULL,

```

## 5. 七项终检

| 检查 | 判定 | 实现 |
| --- | --- | --- |
| **题面逻辑校验** | 题面中的范围/约束与 `spec.json` 一致；样例在题面中出现且与数据一致 | 解析题面 + 比对 spec + 跑样例 |
| **测试点数据分布真实性** | 各子任务分布合理（如随机/构造/极端各占一定比例），不得全部同质 | 统计输入特征（大小、取值分布、图结构） |
| **题目配置可靠性** | 限制、评测模板、checker 配置、分值合计正确 | 读回 OJ 配置逐项校验 |
| **多语言校验** | 标程在 C++/Python/Java 下均满分 | 沙箱多语言编译运行 |
| **解法多样性校验** | 至少 2 种不同算法实现均满分；典型错误解得分符合预期 | 提交矩阵 |
| **数据强度校验** | 暴力/错误解在「应失败」的点上确实失败 | 反例矩阵 |
| **边界条件校验** | 最小/最大规模、极端值、退化结构均有覆盖 | 边界用例集 |
| **人类实测校验** | 未参与设计的真人限时完成，记录用时/得分/代码/意见 | 专用链接 + 记录 |

> 前七项可自动化，「人类实测」不可自动化。这是**唯一能发现「题目表述有歧义」的手段**。

### 5.1 人类实测专用链接

- 生成 `trial_token`（32 字节随机），有效期可设（默认 7 天），一次性或可重入。
- 访问 `/v2/trial/<token>` → 免登录进入某题的**隔离副本**（题目数据与正式无关），带计时器。
- 提交后记录：开始/结束时间、得分、完整代码、语言。
- 结束页强制填写意见（至少一句话）。
- 结果回写到 `oj_authoring_human_trial`，在作者工作台可见。

## 6. 客观题与主观题

### 6.1 客观题

现有 `problem_objective`：

```sql
type     -- 0 单选 / 1 多选 / 2 不定项
content  -- {"description":"", "choice":["","",""]}
answer   -- ["A","B"]
username -- 创建者
```

补齐：`title`、`visibility`、`manage_group_id`、`difficulty`（见 §3.3）。

**新增能力**：支持图片选项（`choice[].image_id` 引用 `AiFile`/filesys），支持解析（`explanation`）。

### 6.2 主观题

现有 `problem_subjective`：

```sql
type     -- 0 文件 / 1 文本 / 2 验收题(排队)
config   -- {maxCount, review_queue, fileList, judgeConfig:[{name,score,answer}]}
description
```

`judgeConfig[].answer` 即**评分标准**。补齐可见性字段后，接入 02 的 agent 批阅（评分标准作为工具输入，产出结构化评分 + 理由，教师复核）。

## 7. 文档 / 图片解析、分割与翻译

### 7.1 输入

支持上传：`pdf`、`docx`、`png/jpg`、`md`、`txt`。

### 7.2 管线

```
上传 → 类型识别 → 分页/分块 → 版面解析 → 文本+图片抽取 → 题块切分 → 结构化题目 → 翻译
```

| 步骤 | 实现 | 备注 |
| --- | --- | --- |
| 类型识别 | `media_type` + magic bytes | 拒绝可执行文件 |
| PDF 文本 | **PyMuPDF**（已在 `requirements.txt`） | 扫描件无文本层则转图片 |
| PDF 页图 | PyMuPDF 渲染 200 DPI | 供 OCR/视觉模型 |
| DOCX | **python-docx**（已依赖） | 保留段落与表格顺序 |
| 图片 OCR | **pytesseract**（已依赖） | 中文需 `chi_sim` 语言包 |
| 版面分析 | 现有 `_call_layout_parsing_api`（`llm_client.py`） | 已存在，复用 |
| 题块切分 | 规则（题号正则）+ 模型（歧义时） | 规则优先，模型兜底 |
| 结构化 | 输出 JSON（题干/选项/答案/解析/评分标准） | schema 强校验 |
| 翻译 | 走默认端口（02），逐块翻译并保留原文 | 术语表可配 |

### 7.3 产物

```json
{
  "blocks": [
    {"index": 1, "page": 3, "bbox": [x0,y0,x1,y1], "image_ref": "file:..."},
    {"index": 2, "page": 3, "text": "1. 下列...", "ocr_confidence": 0.93}
  ],
  "problems": [
    {"no": 1, "type": "objective", "stem": "...", "choices": ["A...","B..."],
     "answer": ["A"], "explanation": "...", "grading_rubric": null,
     "source": {"page": 3, "bbox": [...]}}
  ]
}
```

**保留 `source` 定位**：便于人工核对「模型解析的这块是否对应原文那一段」。

### 7.4 翻译

- 按块翻译，输出对照（原文 + 译文 + 可选双语）。
- **不覆盖原文**，新增 `statement_i18n` 字段/表。
- 术语不一致时给警告，不静默替换。
